---------------------------------------------------------------------
TAG ENTREGA-3-1.0
---------------------------------------------------------------------
NEW FEATURES (lo que están entregando y está funcionando):
* Arquitectura modular monolítica en Elixir 1.20 / Phoenix 1.8 con PostgreSQL como fuente autoritativa, Redis como cache descartable de lectura y Oban como motor durable de trabajos en segundo plano.
* Test automático de arquitectura basado en AST (`test/architecture_boundaries_test.exs`, TASK-045 / PR #113) — equivalente idiomático a ArchUnit — que valida las fronteras entre capas `web`, `domain`, `persistence` (`Repo`/Ecto), `workers`, `providers` y `cache`, con controles positivos y de mutación.
* Auditoría estructurada JSON de Web-Services (`lib/football_market/observability.ex` y `FootballMarketWeb.RequestLogger` en `lib/football_market_web/telemetry.ex`, TASK-037 / PR #102) — equivalente a Spring AOP + Log4j/Logback — registrando `timestamp` UTC, `actor_id` (usuario verificado o `anonymous`), operación (`method` + `route` estable), `parameters` filtrados por allowlist tipada, `status` y `duration_ms` monotónico en todas las respuestas HTTP (incluyendo errores y rechazos), preservando la evidencia financiera append-only.
* Endpoints de monitoreo / equivalentes a Spring Boot Actuators (`HealthController` y `FootballMarket.Infrastructure.Health`, TASK-038 / PR #107 + PR #120):
  - `GET /health/live` (liveness independiente de dependencias).
  - `GET /health/ready` (readiness acotada de PostgreSQL, Redis degradable y Oban).
  - `GET /health/info` (metadatos seguros de aplicación y runtime: `application`, `version`, `elixir`, `otp_release`).
* Métricas operacionales en formato Prometheus (`GET /metrics`, `FootballMarket.Observability.Metrics`, `MetricsController`, `MetricsAuth`, `docs/OBSERVABILITY.md`, TASK-039 / PR #108 + PR #120) — equivalente a Spring Boot Prometheus/Micrometer — protegido con Bearer token (`METRICS_SCRAPE_TOKEN`), exponiendo formato texto 0.0.4 para requests/errores/latencia HTTP, latencia de queries Ecto, memoria y run queues de la BEAM VM, jobs Oban, requests a proveedores externos y hits/misses/errores del cache de ranking (`football_market_ranking_cache_total`). Incluye setup opcional de demostración local en `docs/observability/compose.prometheus.yaml`.
* Optimización de Ranking de jugadores según estrategia activa para alta frecuencia de consultas (`FootballMarket.Ranking`, `FootballMarket.Ranking.Cache`, TASK-041 / PR #110, TASK-042 / PR #111, TASK-043 / PR #112): cache Redis con claves versionadas por configuración activa + revisión (`selection:quotes`), TTL acotado de 30s, coherencia sin side-effects externos dentro de transacciones financieras, fallback transparente a PostgreSQL ante caída de Redis, telemetría hit/miss/error y benchmark reproducible con planes `EXPLAIN (ANALYZE, BUFFERS)`.
* Endpoint administrativo de métricas avanzadas de negocio (`GET /api/business-metrics`, `BusinessMetricsController` y `FootballMarket.BusinessMetrics`, TASK-040 / PR #114): documentado en OpenAPI 3 (`priv/static/openapi.json`), solo para administradores, leyendo un snapshot consistente `REPEATABLE READ, READ ONLY` con agregados de cotizaciones, órdenes condicionales, actividad de portfolios, ingesta de estadísticas y estados de jobs Oban.
* Resiliencia de proveedores externos (`TASK-044` / PR #115), endurecimiento de seguridad API/UI con rate limiting compartido y redacción segura de logs (`TASK-050` / PR #117), paridad API/frontend (`TASK-084` / PR #116) y suite de escenarios completos cubriendo 5 ligas (`PL`, `BL1`, `PD`, `SA`, `FL1`), ingesta idempotente, cotizaciones fechadas inmutables, 4 usuarios, compras de 5 jugadores, portfolios actuales y métricas (`TASK-051` / PR #121).
* Capacidades de Entrega 1 y Entrega 2 retenidas y verificadas: autenticación JWT, API keys y sesiones browser seguras, documentación OpenAPI 3 + Swagger UI (`/docs`), catálogo de 5 ligas europeas, estrategias configurables de valuación (`balanced` y `position_aware`), cotizaciones históricas inmutables, trading atómico idempotente con invariante fijo de 100 tokens, gráficos de portfolio y órdenes condicionales de compra evaluadas por Oban.
* Pipeline de calidad continuo en GitHub Actions (`Quality baseline`, `End-to-end profile`, `SonarCloud`, `ThinFlow required`): formato, compilación con warnings-as-errors, Credo con inventario completo, Sobelow (0 bloqueantes), Dialyzer, cobertura de aplicación y pruebas unitarias, de integración y E2E con Playwright.

NOTES (ej: funcionalidad que falta, alguna consideración especial):
* Equivalencias tecnológicas respecto a la rúbrica redactada originalmente para Spring Boot: Elixir/Phoenix + Logger JSON/Telemetry en lugar de Spring/Log4j/Logback; `GET /metrics` ETS Prometheus 0.0.4 en lugar de Spring Boot Prometheus/Micrometer; `GET /health/live`, `GET /health/ready` y `GET /health/info` en lugar de Spring Boot Actuators; y test AST en ExUnit (`test/architecture_boundaries_test.exs`) en lugar de ArchUnit.
* `GET /metrics` opera en modo fail-closed (retorna HTTP 401) cuando la variable de entorno `METRICS_SCRAPE_TOKEN` no está configurada.
* La vista administrativa en LiveView para las métricas avanzadas (`TASK-073`) no fue incluida en este tag; las métricas avanzadas de negocio están disponibles mediante la API REST `GET /api/business-metrics` (protegida por JWT/API key de administrador).
* Las pruebas automatizadas ejecutan contra fixtures determinísticos locales sin depender de red externa; la sincronización en vivo con proveedores externos requiere credenciales/configuración de entorno y respeta límites de tasa.

KNOWN ISSUES (ej: funcionalidad que saben que están funcionando diferente, algún error conocido en la funcionalidad terminada, etc):
* `GET /api/business-metrics` reporta `basis: "retained_local_records"` sobre los registros actualmente retenidos en PostgreSQL; el pruning periódico de Oban reduce el conteo histórico de jobs completados retenidos.
* Ante indisponibilidad de Redis, `GET /health/ready` informa `dependencies.redis = "degraded"` manteniendo HTTP 200 (`status: "ready"`) y `GET /api/ranking` degrada de forma transparente a lecturas directas sobre PostgreSQL con mayor latencia.
* El servidor Prometheus local de demostración (`docs/observability/compose.prometheus.yaml`) es opt-in y separado del `compose.yaml` principal (que mantiene únicamente PostgreSQL y Redis para el contrato de servicios locales).
