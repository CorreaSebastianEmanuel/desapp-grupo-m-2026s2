# Product Challenge

- **The reproducibility outcomes are not falsifiable yet.** SC-001 promises 100% success on “the documented supported environment,” SC-002 imposes ten minutes, and SC-003/SC-004 require repeated trials, but neither the environment matrix nor a trial protocol, timer boundaries, sample count, or cleanup baseline is defined. A single author-machine run could satisfy the wording while providing weak CP1 evidence. **Recommendation:** the plan must name the supported OS/container-runtime baseline and define an executable acceptance protocol: exact initial state, commands, timeout, expected exit codes/output, cycle count, and evidence retained. Treat the ten-minute measure as a documented manual acceptance check unless CI can reproduce it reliably.

- **Network exposure is a security gap.** The assumptions mention binding “loopback ports,” but FR-002 only requires ports and FR-006 only addresses credentials. Common container port publishing can expose databases on every host interface, making deliberately weak local credentials reachable from the LAN. **Recommendation:** bind PostgreSQL and Redis host ports explicitly to loopback, avoid privileged/default production credentials, and verify the resolved service configuration. Document that defaults are local-only.

- **Development/test isolation is asserted but not fail-closed.** Separate database names satisfy the happy path but do not prevent a malformed test URL from targeting development data; SC-006’s “development records unchanged” is also undefined because this task excludes seed/domain data. **Recommendation:** add a test-environment guard that rejects the development database identity (and preferably requires a test-specific suffix), then prove isolation with a sentinel schema/table or migration metadata created outside the test run—not later product records.

- **“Real application-managed connectivity” is underspecified.** FR-011 does not state whether booting the supervision tree, a Mix task, or a repository/integration test qualifies; success/failure diagnostics and exit semantics are therefore easy to satisfy superficially. **Recommendation:** expose one repository-native verification command that uses the same runtime configuration and client modules as the application, checks both dependencies independently even when one fails, emits no connection secrets, and exits nonzero unless both pass. Keep public health HTTP behavior deferred to TASK-038.

- **The migration baseline lacks an observable target.** “Minimal non-domain schema state” permits a no-op migration, which proves command wiring but not create/apply/reapply behavior or failure reporting. Adding speculative product tables would violate FR-016. **Recommendation:** use a deliberately infrastructure-only probe object if Ecto needs one, state its lifecycle and purpose in the plan, and test ordered application plus idempotent rerun. Do not introduce domain or cache schema.

- **Reset and readiness boundaries need executable safeguards.** “Clearly labeled” reset and “bounded” readiness do not define confirmation, project/volume scoping, or maximum wait. **Recommendation:** scope resources deterministically to this repository, make reset an explicit command naming the local data it destroys, and specify finite health-check retries/timeouts with per-service failure output.
