# Product Challenge

- **“Complete unit test suite” is not presently falsifiable.** FR-005 and the edge cases reject skipped, undiscovered, empty, or prematurely terminated runs, while the handoff merely assumes TASK-001 provides “meaningful tests.” A successful test command can still discover zero tests or silently exclude files, so SC-002/SC-003 would not prove completeness. **Recommendation:** the plan must identify the canonical unit-test command and add deterministic evidence that at least the expected baseline tests are discovered; fail on zero tests. Treat intentionally skipped tests separately from an incomplete run rather than implying that any skip must fail CI.

- **Warning coverage is ambiguous.** FR-004 says “every compiler warning,” but does not say whether this covers application code only, test/support code, generated code, or third-party dependencies. In an Elixir/Phoenix project, dependency warnings may be outside team control, while omitting test compilation leaves a gap. **Recommendation:** make project-owned application, test, and support code warning-fatal under the repository’s locked toolchain; do not expand the gate to dependency-source warnings unless the project already controls them.

- **The trigger may not demonstrate CP1’s green Actions build on the integration branch.** FR-001 requires pull-request validation, while direct pushes are explicitly optional. That can leave the merged `main` revision without its own run, weakening checkpoint evidence and permitting merge-time or branch-only differences to go undetected. **Recommendation:** trigger on pull requests targeting the primary branch and pushes to that branch. Use concurrency keyed by workflow and PR/branch, cancelling superseded PR runs without conflating commit SHAs.

- **“Exactly three categories” risks confusing presentation with execution.** SC-007 can discourage necessary setup (checkout, runtime installation, dependency cache/retrieval), and “one overall result” does not define whether three separately visible checks are required. **Recommendation:** treat the three categories as enforced quality outcomes, not a literal job/step count; setup failures must fail the same required workflow, and category-labelled diagnostics must remain visible.

- **The 100% success criteria overclaim evidence.** SC-001 and SC-003–SC-005 quantify all changes/attempts without an observation window or sample definition. **Recommendation:** acceptance evidence should use one conforming fixture and one controlled negative fixture per defect class on the same pinned toolchain, while ongoing reliability remains an operational property rather than a one-time proof.
