# Product Challenge: SonarCloud Integration

- **The governing count remains underspecified.** CP1 says “fewer than 10 issues”; the spec narrows this to whole-project unresolved issues but does not bind “issue” to SonarCloud types, statuses, branch, quality profile, or API measure. The product handoff explicitly says platform terminology is unconfirmed. Two plausible filters could yield opposite CP1 verdicts. **Recommendation:** the architect must document one authoritative SonarCloud measure/query, its included types and statuses, primary branch, and quality-profile identity. Preserve the 0–9/10+ rule; do not substitute a new-code gate.

- **The promised 9/10 verification is not presently credible.** SC-002 requires controlled live analyses to land exactly on both counts, while rule-profile changes, concurrent analysis, or issue triage can alter totals. Deliberately creating findings may also pollute the project used for CP1 evidence. **Recommendation:** test the threshold decision deterministically with captured/fixture Sonar responses at 9 and 10, then separately verify one real published primary-branch result and record the queried value, revision, profile, and timestamp.

- **“Every pull request” lacks an event matrix.** Human feedback makes all supported PRs internal and mandates analysis, but the criteria do not say how drafts, reopened PRs, synchronization updates, reruns, or canceled superseded runs behave. This makes SC-001’s denominator and FR-010’s governing-result rule untestable. **Recommendation:** define supported PR events and require the latest head SHA’s completed check before merge; canceled older runs may remain visible but must never satisfy that requirement.

- **Failure criteria confuse analysis with CI orchestration.** A canceled superseded run should not pass, but it need not leave an independent visible failure if a newer run governs the same PR. Similarly, safely inducing authentication and timeout failures against the production project is disproportionate. **Recommendation:** distinguish governing-run failure from obsolete-run cancellation and specify a safe test/evidence method for each failure class.

- **FR-009’s “secret-bearing files” exclusion is unsafe and ambiguous.** Repository-owned configuration can be valid analysis input without containing secret values; labeling a path secret-bearing could suppress security findings. **Recommendation:** keep secret values out of version control and logs, and enumerate only generated, vendored, dependency, and build-output exclusion patterns. Use a normal internal-PR workflow context; do not introduce a privileged `pull_request_target` path.

- **Navigation and regression success metrics are weakly operationalized.** SC-006 does not define the starting screen; SC-008’s “100% of regression comparisons” has no comparison procedure. **Recommendation:** start navigation measurement at the PR checks view and identify the unchanged TASK-003 commands/check conclusions used as before/after evidence.
