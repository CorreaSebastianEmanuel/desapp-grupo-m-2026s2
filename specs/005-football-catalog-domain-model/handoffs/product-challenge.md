# Product Challenge

## Material findings

- **In-season transfers have no valid behavior.** FR-009 gives a player exactly one team, FR-010 permits only one player identity per league season, and the assumptions defer transfer history. A footballer moving between teams in the same season therefore cannot be represented without mutating the existing affiliation, rejecting valid provider data, or changing the model. This affects catalog truth and later statistics/ingestion. **Recommendation:** obtain the product decision recorded in `product-decision.md`; the architect should preserve the chosen invariant explicitly and avoid accidentally deciding it through a database constraint.

- **The supported-league constraint is not implementable consistently from the stated data.** FR-002 names five leagues, while FR-003 requires stable codes but defines neither codes nor canonical name/code pairs. Accepting arbitrary codes paired with a recognized name undermines “stable”; enforcing guessed codes invents product data. **Recommendation:** define a single application-owned mapping (including exact normalized codes) as an architectural constant/configuration and test mismatched name/code pairs. If existing course fixtures dictate codes, use those as evidence; this is routine unless external compatibility is mandated.

- **Lookup acceptance is underspecified.** FR-014 asks for each entity’s “business identity” without enumerating each lookup key; FR-015 says filters work individually and in combination but does not define empty filters, unknown values, ordering, pagination, or whether season means `(league, start_year, end_year)` versus an internal ID. “Stable results” in User Story 3 is therefore untestable. **Recommendation:** constrain this task’s persistence API to explicit keys and AND-composed filters; specify deterministic ordering only if returned collections expose order. Treat pagination and HTTP semantics as later-task scope.

- **SC-007 is not reproducible and expands CP1.** “95% within one second” lacks hardware, database state, warm-up, concurrency, query mix, sample count, and percentile definition. CP1 requires a minimum model/player catalog, while database performance validation is separately owned by TASK-043. **Recommendation:** replace this gate at architecture level with query-plan/index evidence for the declared lookup paths and defer SLA benchmarking to TASK-043; do not claim SC-007 from incidental local timings.

- **Atomicity scope is ambiguous.** FR-013 and the edge case require failed “multi-record catalog operations” to roll back, but no such operation is defined and ingestion is out of scope. **Recommendation:** require transactions only for concrete multi-entity domain commands introduced by this task; do not create a speculative bulk-ingestion API.

- **Normalization needs database-level, race-safe enforcement.** Application-only trimming/case checks permit concurrent duplicates, violating FR-003/007/008/010. Unicode case-folding and blank detection are also unspecified. **Recommendation:** choose and document one normalization policy, store or index normalized keys, enforce uniqueness in PostgreSQL, and test concurrent conflicts plus whitespace-only input.
