# Product Challenge: Development Seed Data

- **Normalized matches have contradictory outcomes.** The normalized-identity edge case and SC-004 require reuse, while FR-011 forbids changing the matched record and FR-016 requires the same observable target as an empty-catalog run. An existing `" Demo FC "`/`"demo fc"` identity cannot both retain its literal value and equal the manifest byte-for-byte. FR-014 also leaves “canonical attributes agree” undefined for normalized identity fields. **Recommendation:** obtain the product decision recorded separately, then make the plan define one comparison matrix per entity: identity fields and normalization, exact attributes, relationship checks, and fields ignored during reconciliation. Do not let persistence behavior decide this implicitly.

- **Production safety is weaker than the stated usage boundary.** FR-017 prevents automatic production loading but does not prohibit an operator from invoking the action manually against production. Because this action inserts a coherent but fictional hierarchy, an accidental invocation would compromise catalog integrity without violating the current text. **Recommendation:** decide whether production execution is forbidden. Prefer a fail-closed runtime environment guard plus an explicit non-production invocation path; do not rely only on documentation or startup wiring.

- **“One repeatable action” and “reports” are not testable contracts.** FR-001 does not identify the supported entry point, and FR-014/FR-015 do not define how automation distinguishes success, conflict, and validation failure. A logged message could technically “identify” a conflict yet be unusable by setup scripts. **Recommendation:** the plan should name one supported command/API boundary and require deterministic non-success signaling with entity type and business identity, while preserving the underlying validation cause without exposing credentials or connection details.

- **Concurrent execution is an uncovered boundary.** All-or-nothing rollback addresses one invocation, but two seed actions can race between lookup and insert. **Recommendation:** either guarantee serialized/idempotent concurrent runs (one creator, one successful reuse) or explicitly exclude concurrency while still requiring database constraints and transaction rollback to prevent duplicates and partial state. Add the chosen behavior to verification.

- **SC-006 lacks a reproducible performance oracle.** “Standard local development environment” gives no hardware, database state, or measurement boundary, so the ten-second threshold cannot support an honest pass/fail result. **Recommendation:** define a minimal reference setup and whether database startup/migrations are excluded. CP1 evidence should exercise the documented fresh-database entry point and verify catalog visibility, not only call reconciliation functions in tests.
