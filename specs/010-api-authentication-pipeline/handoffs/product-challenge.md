# Product Challenge: API Authentication Pipeline

- **Transport-layer failures are overclaimed.** The edge cases require “non-text input” and all malformed credentials to produce the generic unauthenticated outcome, but Cowboy/Plug or an intermediary can reject invalid HTTP bytes before the authentication pipeline runs, commonly as `400`. FR-007/SC-002 are therefore untestable as universal statements. **Recommendation:** architect tests every malformed value that reaches Plug; document pre-application HTTP rejection as outside this feature and do not weaken the server parser to manufacture a `401`.

- **Repeated-value detection needs an explicit wire-level boundary.** FR-008 covers repeated headers and multiple values, while intermediaries may preserve duplicate fields or combine them into a comma-delimited value. Treating commas generically as separators is unsafe because credential grammars are opaque. **Recommendation:** inspect all raw values exposed by Plug, reject more than one field occurrence, and let each trusted validator reject any single combined/altered value; add tests for duplicate lines and coalesced values.

- **SC-004 exceeds and ambiguously contradicts the actor contract.** It requires zero identity identifiers outside the protected actor context across “responses” and “diagnostics,” although downstream protected operations may legitimately return account-owned resource identifiers; FR-012 only prohibits authentication processing from emitting account/token/key identifiers. **Recommendation:** scope inspection to authentication-generated responses, metadata, errors, logs, and telemetry. Do not impose a system-wide ban on identifiers through this task.

- **The route-policy audit universe is undefined.** “Every API route” could include unmatched routes, Phoenix-generated/dev-only routes, health/metrics endpoints, or future UI routes. This undermines FR-001/SC-006 and could expand TASK-010 beyond the API boundary promised by FR-015. **Recommendation:** define the audited set structurally as application-owned routes under the REST API scope; require that scope to default to the protected pipeline, with public routes placed in an explicit public scope. Exclude framework/dev/UI endpoints and record each intentional public route.

- **A demonstration endpoint could become accidental product surface.** The product handoff permits a minimal protected test route even though TASK-010 is pipeline infrastructure and catalog endpoints arrive in TASK-011. **Recommendation:** prefer router/connection tests around an existing harmless API endpoint or a test-only probe; do not ship a production endpoint solely to demonstrate authentication.

- **SC-005 is not reproducible as written.** “Normal local operating conditions” and a 95th-percentile sample are undefined, while API-key authentication includes persistence latency. **Recommendation:** treat one second as a coarse regression guard, state dataset, warm-up, sample count, and local dependency state, and avoid architecture or caching justified only by this weak signal.

- **Checkpoint evidence must prove integration, not just helpers.** CP1 requires JWT plus user/API-key creation; unit tests of parsing alone would not show that TASK-008 revocation and TASK-009 expiry are honored at the shared boundary. **Recommendation:** include integration tests using both authoritative capabilities, immediate revoked-key rejection, generic response equivalence, and protected-operation non-execution.
