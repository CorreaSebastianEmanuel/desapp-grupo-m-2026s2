# Research: Composable Player Catalog Filters

## Decision: Extend the existing ordered page query

**Rationale**: `Catalog.Query.player_page/2` already joins player → team → season → league and position, preloads the public representation, and orders by `lower(btrim(display_name)), id` with a keyset seek and a bounded limit. Optional predicates on the joined IDs give exact AND filtering before page selection. Existing player order and foreign-key indexes provide the initial access paths.

**Alternatives considered**: `Query.players/1` already filters these IDs but orders by player ID and returns an unbounded list. Post-page filtering breaks page fullness and traversal. Separate relationship-existence queries disclose information and add round trips. Add expression indexes only after a measured plan demonstrates need.

## Decision: Canonical UUID inputs at the transport boundary

**Rationale**: Parse raw query pairs to retain multiplicity and bracket-form evidence. Match one ASCII UUID in 8-4-4-4-12 hex shape, with no surrounding whitespace; then canonicalize via `Ecto.UUID.cast/1`. Fixed validation order implements FR-012 regardless of query-string ordering. Unknown well-formed IDs pass to SQL and produce empty pages.

**Alternatives considered**: Phoenix's decoded parameter map can collapse repeated keys. Lookup during validation would turn absent relationships into distinguishable errors. Name/code filtering would be ambiguous across seasons.

## Decision: Preserve v1 and add filter-bound v2 cursor payloads

**Rationale**: TASK-011 v1 tokens contain only version, list scope, and the normalized ordering anchor in an authenticated encrypted envelope. Unfiltered encoding and decoding can remain byte-compatible. A filtered v2 payload adds only canonical present filter names and UUIDs; equality against the request's normalized map is checked before SQL. Page size and actor stay unbound as in TASK-011. The existing test secret is fixed, so a literal token generated by the unchanged encoder provides genuine migration evidence. Current checkout lacks fetched Mix dependencies; fixture generation belongs at the start of implementation, before changing the module.

**Alternatives considered**: Reinterpret v1 as filtered would permit cross-filter continuation. Replace all tokens with v2 would violate existing-cursor compatibility. A hash of filters is compact but increases collision and canonicalization complexity without a payload-size need. Server-side cursor state adds unnecessary persistence and expiry behavior.

## Decision: Fixed local latency protocol

**Rationale**: Use exactly 100,000 deterministic players distributed as five leagues × two seasons × ten teams × 1,000 players, with four positions represented equally within each team. This yields broad, medium, and narrow filters with known selectivity. For league, position, team, league+position, team+position, and league+team+position, measure first and continuation pages of size 100 after ten warm-ups and 100 sequential samples each. The 95th sorted sample must be at most two seconds in every case. Record the specified machine/database conditions and actual fixture counts. `Phoenix.ConnTest` covers the in-process authentication, controller, query, and rendering pipeline; it excludes network latency.

**Alternatives considered**: TASK-011's one-team/one-position fixture and nonasserting diagnostic miss selective filters. A production/concurrent SLA is not stated by the spec. Lowering the two-second threshold or narrowing cases would change the acceptance criterion.

## Decision: Client ID prerequisite

**Rationale**: Existing player list representations contain league, team, and position IDs. A client can first obtain an unfiltered list and use those IDs in subsequent filtered requests. The API does not promise complete enumeration of all selectable IDs.

**Alternatives considered**: New discovery routes or UI would expand TASK-012 beyond FR-016.
