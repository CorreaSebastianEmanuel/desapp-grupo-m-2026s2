# Product challenge: TASK-013

- **Credential selection can mislead readers.** FR-004 requires one selected method, while the edge cases say mixed headers receive 401. An OpenAPI security `OR` declares alternatives but does not establish that the interactive page will send only one header after a reader has entered both credentials. **Recommendation:** Verify the page's actual request headers when switching from JWT to API key and back. Use an existing UI only if it enforces one active method; otherwise add a small credential selector or clearing behavior. Keep this within documentation UI scope.

- **Schema validity is weaker than contract fidelity.** FR-015 and SC-003 require alignment with live routes and responses. An OpenAPI validator cannot establish authentication-before-validation, 400 error priority, cursor/filter binding, exact object keys, or the 401 challenge. **Recommendation:** Pair schema validation with deterministic requests that cover those rules and all five list error codes; compare status, headers, and response structure. Compare the documented operation set specifically with the two CP1 catalog routes in FR-003, so unrelated Phoenix or documentation routes do not create false failures. The browser check should exercise both credential methods.

- **Public interactive documentation handles secrets.** FR-001 makes the page public and FR-002 lets it submit reader-supplied credentials; the edge cases prohibit credentials in shareable URLs. Third-party page assets, persistent browser storage, and request logging could still expose those values. **Recommendation:** Serve trusted assets locally, avoid storing or preloading credentials, and verify credentials appear only in the intended request header. Check that example payloads, page configuration, URLs, and failure output contain no real credential. These are implementation safeguards for the already specified public page.

- **The discovery criterion needs repeatable evidence.** SC-001's “within three minutes” depends on a known starting address; SC-002 additionally needs valid credentials, while FR-003 and the assumptions exclude HTTP issuance operations. **Recommendation:** Publish both documentation addresses in project instructions and provide preprovisioned test credentials through the existing test setup for the CP1 acceptance walkthrough. Do not add issuance routes to make the demonstration convenient.
