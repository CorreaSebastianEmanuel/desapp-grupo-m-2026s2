# Product Challenge: CP1 Test and Coverage Profiles

- **Snapshot provenance is not yet falsifiable.** FR-016/017 require a hash of the “relevant” working-tree diff, but the Assumptions and product handoff defer the input set to planning. It is therefore unclear whether test support, test configuration, dependency locks, browser-contract assets, or untracked execution inputs can change while a report retains the same provenance. A report could be accurately hashed yet wrongly presented as the tested state. **Recommendation:** make the fingerprint’s inputs and untracked-input policy an explicit architecture decision and add mutation tests proving each included input changes provenance and excluded generated output does not. See `handoffs/product-decision.md`.

- **The secrecy outcome lacks a bounded output/artifact contract.** FR-006/007 and SC-005 prohibit sensitive material in every emitted or retained output, but do not identify retained locations or define what “test verification material” covers. Child stderr, exception formatting, command echoes, generated reports, and CI artifacts have different interception points; an after-the-fact sanitizer cannot meet the stated “before emission” rule. **Recommendation:** require one controlled capture-and-release path, a named list of permitted sanitized artifacts, and generic diagnostics on capture/sanitization failure. Use injected sentinel values across stdout, stderr, exceptions, command lines, and missing-prerequisite failures to demonstrate no release channel leaks.

- **Coverage’s percentage has no defined measurement unit.** FR-014 and SC-006 require an overall percentage and source-level executed/unexecuted information, but not whether the percentage is line, branch, function, or statement coverage, nor the numerator/denominator presentation. A partially executed source can satisfy the wording while making two tools report materially different “overall” percentages. **Recommendation:** select one collector-supported unit (prefer line coverage for this CP1 transparency report), publish its numerator and denominator, and define per-source status from that same unit.

- **“Every automated CP1 test” has no enforceable population boundary.** FR-003 and the Edge Cases require exact-one classification, but do not establish how newly added or dynamically discovered CP1 tests are prevented from sitting outside both profiles. **Recommendation:** maintain an executable classification/discovery manifest or naming convention with a check that fails for unclassified, duplicate, skipped, or undiscovered CP1 tests.
