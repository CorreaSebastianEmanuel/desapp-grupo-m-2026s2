# Architecture Handoff: CP1 Acceptance Evidence

## Decisions not obvious from the plan

- Treat the user's statement that the required human check is approved as approval of the product-decision recommendation. This matches existing ADR-0001: whole-project `open_issues` on the exact integrated `main` analysis.
- `acceptance.json` generated by the evaluator is authoritative; Markdown is a projection. Never allow a prose-only override of a failing row.
- Final PASS is necessarily post-merge because the authoritative Sonar population is the exact candidate's `main` analysis. PR and working-tree runs are preflight only.

## Risks

- GitHub artifact retention may be policy-limited. Implementation must configure the maximum repository-supported retention and keep stable README/workflow navigation. If course requirements demand permanence beyond hosted-run retention, request a product decision before adding a release, Pages site, or external store.
- Coordinating separate quality/Sonar/acceptance workflows can accidentally consume a successful run for another SHA. Prefer reusable workflow execution or explicit API lookup keyed by full SHA and terminal conclusion; ambiguity is non-pass.
- Demo secrets can leak through shell tracing, Phoenix parameter logs, SQL debug logs, browser traces, or assertion output. Child streams must stay private even on failure; scanning is a final guard, not the primary control.

## Implementation guidance

- Use standard-library Python and strict per-receipt schemas; reject extra sensitive-looking fields, unknown enums, duplicate IDs, and relative/ephemeral hosted URLs.
- Keep the disposable demo database target explicit and guarded. Never reset a developer/default database by inference.
- Generate unique demo identities without embedding passwords in command arguments. Preserve only behavior IDs and aggregate counts.
- Test the publication sequence with synthetic workflow/receipt fixtures locally; hosted PASS still requires real post-merge evidence.
