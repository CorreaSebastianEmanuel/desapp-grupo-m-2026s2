# Product Challenge: CP1 Acceptance Evidence

- **The candidate-revision rule is circular unless the evidence publication sequence is explicit.** FR-005/017 require all evidence to match one commit, but committing the completed acceptance record changes the revision after checks were captured. A working-tree label cannot yield a pass under the stated assumptions. **Recommendation:** architect a two-phase process in which the final evidence-bearing commit receives fresh CI/Sonar results and any local results are rerun against that exact commit; do not copy earlier green results forward.

- **There is no defined evaluator for fail-closed aggregation.** The spec says the overall result is “calculated” and SC-007 requires controlled stale/failure evaluations, yet FR-001 only requires documents. A manually edited PASS can contradict missing or stale entries with no detectable failure. **Recommendation:** define a small machine-checkable manifest plus validator, or an equally explicit review algorithm with fixtures proving every non-pass state. Generated prose may summarize, but must not be the source of truth.

- **The SonarCloud threshold is materially ambiguous.** `docs/CHECKPOINTS.md` says “fewer than 10 issues”; FR-008 adds “unresolved” but does not define main versus feature branch, overall versus new code, issue types, accepted/won't-fix statuses, or which analysis is governing. Each choice can reverse acceptance. **Recommendation:** resolve the decision recorded in `product-decision.md`, then name the exact Sonar project, branch/PR, analysis identifier, metric/filter, statuses, and retrieval timestamp.

- **Several checks risk silently enlarging CP1.** CP1 names API-key creation and player catalog; FR-011 makes revocation a checkpoint gate, while FR-012/SC-006 require pagination and an extensive filter matrix. Those may be valid prerequisite regressions, but the current documents do not establish that each is independently necessary to pass CP1. **Recommendation:** distinguish checkpoint gates from supporting regression evidence and trace every expanded behavior to its prerequisite contract; do not fail CP1 for an extra behavior unless that contract makes it part of the named obligation.

- **Repeatability and timing criteria lack controlled boundaries.** “Clean checkout,” “prerequisites are available,” two runs, and the 20-minute limit do not state whether dependency download, service startup, hosted latency, or teardown count. Existing data can also mask preparation failures. **Recommendation:** define an isolated starting state, clock start/stop, supported environment, network assumptions, reset semantics, and exact seed invariants/counts.

- **Credential-safe evidence needs prevention, not inspection alone.** The demo must use secrets while SC-008 forbids them in retained output. Shell tracing, command echo, HTTP transcripts, and CI logs can leak even if the guide avoids printing values. **Recommendation:** use transient environment/process inputs, disable tracing, capture only redacted assertions, scan artifacts before publication, and invalidate/delete unsafe captures with credential rotation guidance.
