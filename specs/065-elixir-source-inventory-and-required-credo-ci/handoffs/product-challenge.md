# Product challenge — TASK-065

- **Effective file list needs an observable oracle.** FR-003/004 and SC-001 require reconciliation against the files Credo actually analyzes, while the spec does not say how the standard invocation exposes that set. Do not treat the inventory or a separately maintained list as proof of Credo inputs. Architect should select and document a same-revision method that establishes the exact CLI input set, then test added, removed, excluded, and mismatched paths; fail closed if completeness cannot be established. Evidence: spec FR-003/004, edge case on incomplete Credo output, and SC-001.
- **Exclusion reasons need per-path accountability.** FR-005 says every excluded tracked Elixir file has a specific reason, but the acceptance scenarios could be read as accepting a general category explanation. Require each excluded path to resolve to an explicit, reviewable reason and make unknown paths/reasons fail. This prevents a broad generated/vendor rule from masking a maintained file. Evidence: TASK-065 Outcome and spec FR-002/005, including the generated/vendor/build-output edge case.
- **Evidence retention is underspecified.** Spec assumptions allow an artifact “or equivalent output retained by the existing workflow,” but no acceptance criterion distinguishes durable, complete evidence from transient or truncated logs. Architect should choose the smallest existing-workflow mechanism and verify a reviewer can retrieve the triggering revision, full file list, exclusions, and result after the run. Evidence: spec User Story 1 and FR-009; TASK-065 Outcome requires revision-associated CI evidence.
