# Product Challenge

1. **Quote eligibility relies on an unstated success contract.** FR-003 excludes failed or incomplete calculations and requires a successfully committed quote, but neither the spec nor the product handoff identifies the persisted outcome/state that proves this. The source backlog (TASK-033) only says “latest valid quotes.” If history can retain failed attempts or partial results, implementations could rank different rows while each claims compliance. **Recommendation:** architect should bind eligibility to the existing immutable quote contract’s committed-success state and cite its concrete invariant; do not infer success from a positive amount or effective time alone. If the existing contract cannot distinguish these cases, return that as a product gap before implementation.

2. **The concurrency acceptance criterion needs an observable race oracle.** Scenario 9 requires a consistent snapshot during activation changes, but does not state whether the read may return the complete old configuration or must reflect the new one once activation commits. A test that only checks “no mixed quotes” could pass without establishing when the snapshot is taken. **Recommendation:** define the read’s linearization point as its database snapshot start (or another explicit atomic boundary); permit either complete version when activation races, require its reported configuration and quotes to agree, and test both orderings. This is an implementation/test boundary, not a need for a new product policy.
