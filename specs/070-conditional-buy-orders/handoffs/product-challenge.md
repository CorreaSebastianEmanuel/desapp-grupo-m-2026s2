# Product Challenge

- **“Promptly” has no testable boundary.** The edge case says an already-qualifying order is evaluated “promptly,” while TASK-059 and the product baseline disclaim a real-time execution guarantee. A user could read this as an execution latency promise. **Architect:** interpret this as durable eligibility/scheduling after creation, with no completion deadline; align TASK-060’s handoff and tests to that interpretation. If a latency promise is intended, it needs an explicit measurable target and is a product-level change.
- **Due expiry must dominate other evaluation outcomes.** Acceptance scenario 3 says a missing quote or above-limit quote leaves an order pending, while FR-012 and the expiry edge case require an order evaluated at/after expiry to become terminal `expired`. **Architect:** make expiry the first eligibility gate and include a due order with no quote or an above-limit quote in the evaluator boundary cases, so it cannot remain pending or be rejected for funds/inventory after expiry.
- **Multi-order contention has intentionally variable winners.** The spec promises no global order priority but requires that competing orders cannot overspend or exceed supply. **Architect:** tests should assert invariant preservation and each order’s valid terminal/pending outcome without encoding an unstated winner or priority policy.
